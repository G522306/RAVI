How it works

Access that starts with a reason and ends on its own.

Nobody holds a production password. Each piece of access is asked for, approved by a person, scoped to columns, and gone when the clock runs out.

01 · REQUEST

Ask for exactly what you need

Pick the database, the tables and the columns, how long you need them, and why. Read or write is part of the request.

Engineer · Sentry web app
02 · APPROVE

A person signs off

The policy engine routes the request. Columns marked PII, FINANCIAL or SECRET always need a human approver.

Approver · role-based
03 · CONNECT

Use your normal SQL client

Sentry issues a short-lived token. Connect to the Postgres gateway with psql, DBeaver or anything that speaks the Postgres protocol.

Engineer · port 6432
04 · EXPIRE

Access closes itself

The grant expires on time or can be revoked early. The gateway picks up the change within seconds, and the full query history stays in the audit log.

AI agents

Let AI work with your data without handing it your database.

Coding assistants and AI agents are starting to query production. Sentry treats an agent like any other client: it gets a scoped, approved, short-lived grant, and the proxy checks every statement it writes.

  • No standing credentials for agentsAn agent connects with a short-lived token instead of a database password it could leak, log or reuse.
  • Only the columns you grantedA hallucinated query or a prompt-injected instruction can't reach a table or column outside the grant. The proxy refuses it.
  • A person approves sensitive dataColumns marked PII, FINANCIAL or SECRET always need a human approver, whoever asks for them.
  • No surprise writes or schema changesRead-only grants refuse UPDATE and DELETE, and the gateway's upstream role can't run DDL, so a stray DROP TABLE goes nowhere.
  • Every agent query on the recordEach statement an agent runs, allowed or refused, lands in the append-only audit log with its grant and reason.

Sentry doesn't read prompts or use AI to spot attacks. It limits what any client can reach, whether a person or a model is writing the SQL.

Guarantees

Built so a mistake stays small.

The proxy is the front line. The rest of the design assumes it could fail and limits what that would cost.

fail-closed · 30s

Fails closed

If the gateway loses the control plane for 30 seconds, it stops serving queries instead of guessing.

UPDATE · DELETE · TRUNCATE ✕

Append-only audit

The audit table rejects updates, deletes and truncates. Allowed and refused queries are both recorded.

SHA-256

Tokens stored as hashes

Connection tokens are kept only as SHA-256 hashes, so the platform database never holds a usable token.

AES-256-GCM

Encrypted resource passwords

The credentials Sentry uses to reach your databases are encrypted at rest.

no DDL upstream

Limited upstream role

The gateway's own database role cannot run DDL, and dangerous functions are blocked at the parser.

OIDC · Okta · Keycloak · OneLogin

Your identity provider

Where it stands

What ships today, and what to change before it faces a network.

Sentry ships as a Docker Compose kit tuned for a local demo. The access model is complete. The defaults are for trying it out, so plan on a hardening pass before anyone else can reach it.

In the kit

  • Postgres as a protected resource (other databases are not supported yet)
  • Web app for requests, approvals, grants and audit
  • Policy engine with column classification
  • SQL-aware Postgres gateway on port 6432
  • Built-in OIDC server, plus Okta, Keycloak and OneLogin SSO
  • A demo "Production Payments" database to try it against

Before shared use

  • Generate your own signing keys, encryption key and passwords (the compose file ships public demo values)
  • Start from a fresh volume with DEMO_DATA=false (demo accounts include an admin)
  • Turn on TLS for the gateway, web app and auth, with REQUIRE_TLS=true and secure cookies
  • Bind ports to localhost or a private interface
  • Enable rate limiting and add Redis
  • Ship the audit log to a separate store and back up the platform database

Try it locally

Running in a few minutes.

Load the prebuilt images, start the stack, and sign in at localhost:3000. You need Docker, and on Windows a bash shell such as Git Bash or WSL.
